## 1. 五分钟接手顺序

每次开始产品、代码、配置、测试或部署工作时，按以下顺序阅读：

1. [`governance.md`](governance.md)：文档与开发必须遵守的同步规则；
2. [`current.md`](current.md)：当前分支、阶段、阻塞项和下一步的唯一状态来源；
3. [`roadmap.md`](roadmap.md)：先做什么、何时允许开始、何时算完成；
4. [`product/PRD.md`](product/PRD.md)：长期产品定位、用户问题、需求和范围边界；
5. [`product/TECHNICAL_SPEC.md`](product/TECHNICAL_SPEC.md)：当前代码契约、架构、安全和部署边界；
6. 与本次任务直接相关的功能设计与实施计划。

如果文档与代码冲突，先按 `governance.md` 记录差异，再以代码和自动化测试作为运行事实修正文档；不得用旧设计快照覆盖新实现。

## 2. 当前项目的一句话

WePicTool（小程序展示名「滑一叠」）是微信叠图玩法生成器：用户先完成素材或文字创作，再预演朋友收到后的滑动效果，把带可见序号的图片按叠保存，最后回微信自行勾选“发送后合并展示”。

当前可继续开发和测试的集成基线是 `main`，已包含穿搭整理、分层云换装、趣味字画和统一导出。代码已合并，但仍未部署或发布；精确证据边界以 [`current.md`](current.md) 为准。

本地继续开发与验证从仓库根目录的 `main` 建立新的 `codex/` 功能分支；`.worktrees/fun-text-stack-phase1` 等来源工作树只保留为历史追溯点。

## 4. 统一状态词

所有长期文档统一使用以下状态，避免把“写完代码”误写成“功能完成”：

| 状态 | 含义 |
| --- | --- |
| `草案` | 已形成方向，等待用户确认，不得据此实施产品或架构变化 |
| `已确认` | 设计边界已确认，可以编写实施计划 |
| `实施中` | 代码或配置正在修改，不能作为稳定基线 |
| `分支已实现` | 功能分支代码与规定的自动化检查通过 |
| `外部验收中` | 仍缺开发者工具、真机、云端或真实微信证据 |
| `可合并` | 代码审查、完整检查和必需外部验收均通过 |
| `已合并` | 已进入 `main`，但未必已发布 |
| `已发布` | 已部署且用户可访问；只有此状态才进入正式变更摘要 |
| `暂缓/已替代` | 不再进入当前路线；保留历史证据，不继续扩展 |

## 6. 继续开发的默认路线

1. 从 `main` 新建短生命周期 `codex/` 分支处理后续缺陷，不再向历史来源分支追加代码；
2. 用户确认 [`product/DESIGN_SYSTEM.md`](product/DESIGN_SYSTEM.md) 后，再编写“无视觉变化”的令牌与共享组件迁移计划；
3. 按 [`roadmap.md`](roadmap.md) 完成首页、预览和三玩法统一导出的开发者工具、iOS、Android、真实微信验收；
4. 决定个人/企业主体、趣味字画 P2.2 是否进入发布包，以及入口 flag 默认值；
5. 仅在纳入发布范围后部署并验证对应云函数/云托管，并让发布模式预检通过；
6. 发布门禁全部通过后再上传体验版、提交审核和发布；实际发布后更新状态与版本摘要。

任何新功能都必须复用首页任务选择、统一叠图预览、manifest 导出、保存引导、记录和安全门禁；不得为单个玩法复制一套页面外壳或保存管线。
