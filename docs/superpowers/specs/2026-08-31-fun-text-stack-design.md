# 趣味字画滑卡设计说明

**日期：** 2026-08-31
**状态：** 用户已于 2026-09-01 确认；阶段一分支代码与自动化已完成并进入 `codex/unified-stack-export`，待云端、双端和真实微信验收
**替代功能：** 大字滑卡（`bigtext` / `big-text`）
**建议用户名称：** 趣味字画
**一句话介绍：** 输入一句话，选一种表达感觉，自动得到三套可以在微信里滑着看的趣味卡片。

## 1. 设计结论

旧「大字滑卡」不继续沿着“一字一图、固定字体、固定主题”的方向迭代。它保留为技术实验和历史证据，其首页功能位、产品描述和后续实施目标由「趣味字画」替代。

新功能不是缩小版图片编辑器，而是一个“微信聊天表达编排器”：用户给出一句原话和大致情绪，系统自动决定如何拆句、在哪里停顿、怎样制造悬念或反转、每张卡承担什么角色，并把文字、背景、贴纸和涂鸦组合成一叠有顺序的图片。用户可以直接使用，也可以在生成后做少量定制。

默认主链路固定为：

```text
输入一句话
  → 选择一个组合表达标签（可跳过，默认“随机好玩”）
  → 自动生成三套真实可滑候选
  → 选中一套
  → 直接预览/保存，或进入“自己改改”
  → 按顺序保存
  → 回微信勾选“发送后合并展示”
```

首版采用“规则 + AI 文案规划 + 确定性场景渲染”的混合架构：AI 只输出结构化的卡片方案，不直接生成带中文文字的最终图片；字体、背景、贴纸、涂鸦和导出图片全部由可控渲染器生成。

## 2. 为什么替换旧大字滑卡

### 2.1 旧功能解决了什么

`codex/bigtext-handwrite` 已验证以下能力：

- 1–20 字输入、内容安全检查和任务状态；
- 云托管加载授权中文字体并稳定输出 1080×1080 PNG；
- 确定性字形偏移、旋转、颗粒效果和 12 个程序化贴纸；
- 模板结果、微信叠图预览、按序保存和本地记录；
- 服务未部署、审核失败、渲染失败和保存失败的基础处理。

这些能力是新功能的技术种子，不应从零重做。

### 2.2 旧功能为什么不满足目标

| 旧行为 | 问题 | 新行为 |
| --- | --- | --- |
| 按字符机械拆分 | 没有故事、停顿和反转，长句滑动疲劳 | 按语义和叙事角色拆成 3–8 张 |
| 用户先选固定主题 | 用户仍需要理解设计参数 | 用户只选“想怎么说”，系统自动配视觉 |
| 每次只得到一套结果 | 用户无法比较，也不容易相信结果会有趣 | 同时给出三套结构明显不同的候选 |
| 字体是主要视觉变化 | 即使是手写字体，重复使用仍显单调 | 字感效果 + 背景 + 贴纸 + 涂鸦 + 版式共同表达 |
| 贴纸由随机数自动放置 | 有变化但没有语义，也不能调整 | 按卡片角色自动搭配，并允许轻量编辑 |
| 结果页才看到完整效果 | 用户在生成前不理解玩法 | 首页先提供无需输入的真实滑卡示例 |

### 2.3 与普通图片编辑软件的差异

普通编辑器的起点是空画布，用户要自己选择字体、字号、颜色、贴纸、位置和图片顺序。趣味字画的起点是“我想对朋友说什么”，输出物不是一张图，而是一个已经编排好的接收者体验。

产品只对以下四件事负责：

1. 把原话改编成适合滑动的节奏；
2. 同时给出三种可比较的表达方案；
3. 自动完成 90% 的视觉搭配；
4. 确保结果能预览、按顺序保存并在微信中正确使用。

产品明确不以字体数量、贴纸数量、滤镜数量或自由画布能力与 Canva、美图、醒图等工具竞争。

## 3. 目标、非目标与成功标准

### 3.1 目标

- 第一次打开的用户无需阅读说明，通过首页示例滑一次就理解产品。
- 用户只输入一句话也能完成生成，情绪标签不是必填表单。
- 每次生成三套叙事结构和视觉语言都明显不同的候选。
- 每套候选包含 3–8 张卡，且保留用户原意，不为了反转擅自改变事实。
- 用户选中后可以零编辑直接导出，也可以只改背景、字感、贴纸、涂鸦和单卡文字。
- 预览、编号保存、发送引导和记录复用统一叠图管线。
- AI 不可用时仍然能通过规则模板生成可用结果。

### 3.2 非目标

- 不做自由尺寸、无限图层、蒙版、曲线、调色和滤镜等通用修图功能。
- 不让用户在生成前逐项选择字体、背景、贴纸、颜色和版式。
- 不用 AI 生图直接生成包含最终中文文字的卡片。
- 不承诺小程序直接把图片发到聊天，也不控制微信侧封面和滑动状态。
- 首版不做模板商城、付费、账号、云端历史同步或创作者社区。
- 不直接复刻小红书案例中的字体、贴纸或受保护素材。
- 不做恐怖惊吓、恶意羞辱、冒充聊天记录或可能造成真实误导的整蛊。

### 3.3 首版成功标准

首版不以收入或大规模用户指标为目标，以“个人项目能稳定玩起来”为标准：

- 示例路径：打开首页后一次点击即可进入可滑示例，不要求登录、输入或相册权限；
- 创作路径：输入一句话后，最多再做一次表达选择即可看到三套候选；
- 候选质量：三套方案的拆句结构、结尾落点和视觉包不能只是换颜色；
- 可用性：关闭 AI 或模拟 AI 失败时，规则兜底仍可完成全链路；
- 可控性：用户能修改一张卡的文字、背景和装饰，而无需面对完整图层面板；
- 导出：iOS 和 Android 均能完成生成、预览、按序保存和微信真机发送；
- 一致性：相同候选在预览和最终 PNG 中的文字、图层顺序和主要位置一致。

## 4. 产品内容模型

趣味字画把“玩法”和“视觉”分开管理，避免每增加一种背景就新增一个首页功能。

### 4.1 表达标签

用户看到的是组合后的自然语言标签，不要求分别理解“情绪”“结构”“模板”：

| 标签 | 默认叙事倾向 | 典型用途 |
| --- | --- | --- |
| 随机好玩 | 从可用策略中自动挑三种 | 不想做选择，直接看结果 |
| 搞怪反转 | 悬念、误导、末卡翻转 | 日常逗朋友、嘴硬表达 |
| 可爱直球 | 逐步靠近、真心落点 | 想念、感谢、夸奖 |
| 暧昧试探 | 留白、半句、轻微反问 | 表白前试探、情侣聊天 |
| 抽象发疯 | 伪清单、错位逻辑、夸张情绪 | 群聊、好友玩梗 |
| 温柔祝福 | 递进、祝愿、收尾插画 | 生日、节日、安慰 |
| 嘴硬心软 | 先否定、再撤回、最后真心 | 道歉、想念、和好 |

首版只实现其中四个：随机好玩、搞怪反转、可爱直球、嘴硬心软。其余标签在基础策略质量稳定后再开放。

### 4.2 叙事策略库

表达标签不是直接对应一套固定文案，而是映射到多个可复用策略：

| 策略 ID | 结构 | 示例落点 |
| --- | --- | --- |
| `hard_turn` | 肯定 → 否定/误导 → 停顿 → 撤回 → 真心 | “不想见你 / 才怪” |
| `suspense_reveal` | 悬念 → 递进 → 靠近 → 揭晓 | “有件事 / 忍很久了 / 我想见你” |
| `fake_checklist` | 伪标题 → 普通事项 → 异常事项 → 置顶结果 | “今日待办 / 吃饭 / 发呆 / 见你” |
| `visual_pause` | 文字铺垫 → 纯涂鸦停顿 → 核心句 | 中间用心形或箭头制造滑动停顿 |
| `repeat_escalate` | 重复短句 → 字号/数量递增 → 情绪爆点 | “想 / 有点想 / 很想” |
| `soft_direct` | 称呼 → 小事 → 感受 → 直接表达 | 温柔直球，不强行反转 |

每个策略声明适用标签、最少/最多卡数、允许的卡片角色和兜底拆句方式。首版先实现前四个。

### 4.3 卡片角色

每张卡必须有明确作用，视觉匹配不直接依赖卡片序号：

- `hook`：封面悬念，负责让收图人愿意滑；
- `build`：补充信息或递进；
- `misdirect`：制造轻微误导；
- `pause`：用短词、留白或纯涂鸦停顿；
- `reveal`：揭晓真正意思；
- `ending`：表情、祝福或余韵收尾。

### 4.4 视觉包

视觉包定义一整套兼容关系，不让用户逐项拼参数：

| 视觉包 | 背景 | 字感 | 自动装饰 |
| --- | --- | --- | --- |
| 粉色便签 | 纸张、便签、胶带 | 马克笔、圈画强调 | 爱心、花朵、手绘箭头 |
| 黑板乱写 | 深色黑板、粉笔灰 | 粉笔、重写、下划线 | 闪电、星星、叉号、箭头 |
| 剪贴报纸 | 米白纸、剪贴色块 | 剪纸字、印章、错位排版 | 胶带、报纸边、图钉 |
| 发疯草稿 | 方格纸、皱纸 | 抖动描边、重复字影 | 爆炸线、问号、乱线 |
| 温柔手账 | 浅色纸、柔和渐变 | 细马克笔、高光 | 小花、云、星点、心形 |

首版上线前三包；后两包属于内容扩展。视觉包包含背景、文字效果、色板、版式槽位、贴纸白名单、涂鸦白名单和每种卡片角色的默认构图。

### 4.5 素材资产

素材分为四类：

1. **背景**：纯色、渐变、纸张纹理、便签框和拼贴底板；
2. **贴纸**：完整的小图形，可移动、缩放、旋转；
3. **涂鸦**：箭头、圈线、爱心线稿、爆炸线、下划线等透明矢量/位图；
4. **字感效果**：马克笔、粉笔、剪纸、印章、抖动描边、高光等渲染配方。

首版建议准备：3 个完整视觉包、每包 4–6 个背景变体、24 个贴纸、12 个涂鸦和 4 种字感效果。素材只使用项目自制、许可明确或保留完整生成记录的资源。

## 5. 用户交互设计

### 5.1 首页：先展示效果，再要求输入

首页的趣味字画入口不是一张功能说明卡，而是一叠可以直接滑动的真实示例：

```text
我今天
  → 不想见你
  → ……
  → 才怪
  → ❤
```

示例上方只显示“滑一下看看”，滑到反转卡后出现“把你的话也变成一叠”。点击示例或按钮可一键带入示例文案进入候选页，不需要相册权限。

正式创作区只保留：

- 一句话输入框，示例占位“比如：我今天想见你”；首版接受 1–40 个 Unicode 字符，去掉首尾空白但保留句内空格和标点；
- 横向表达标签，默认选中“随机好玩”；
- 主按钮“帮我变成一叠”。

背景、字体、贴纸、卡片数量和反转结构均不在首屏询问。

### 5.2 候选页：三套方案必须真的能滑

候选页纵向展示三套独立的小牌堆，每套都能左右滑动，不使用只展示封面的静态缩略图。

每套只显示：

- 一个区别明确的方案名，如“嘴硬一下”“悬念揭晓”“今日待办”；
- 当前卡片画面和 `1/5` 进度；
- “用这套”按钮；
- 次级入口“再来三套”。

三套候选必须使用不同叙事策略；视觉包尽量不同，但“不同”不能仅由换背景颜色实现。用户点击“用这套”后直接进入完整微信预览，页面底部提供“保存这一叠”和“自己改改”。

### 5.3 示例：同一句话的三套自动结果

输入：“我今天想见你”，标签：“搞怪反转”。

候选 A「嘴硬一下」：

```text
我今天
→ 不太想
→ 见你
→ ……
→ 才怪
→ ❤
```

候选 B「靠近一点」：

```text
今天有件事
→ 忍很久了
→ 你靠近点
→ 再近一点
→ 我想见你
```

候选 C「今日待办」：

```text
今日待办
→ 吃饭
→ 发呆
→ 假装很忙
→ 见你（已置顶）
```

三套方案都保留“今天想见你”的核心意思，但采用不同的滑动节奏、结尾结构和视觉隐喻。

### 5.4 “自己改改”：有边界的轻量编辑器

编辑器默认只展示当前卡片和五个一级动作：

1. **改文字**：修改本卡文字，显示建议长度，不自动重写其他卡；
2. **换背景**：只展示与当前视觉包兼容的背景，也可“一键整叠更换”；
3. **换字感**：切换预设效果，不展示字体文件名、描边宽度等参数；
4. **贴纸涂鸦**：从推荐、贴纸、涂鸦三个小列表添加，可拖动、缩放、旋转和删除；
5. **调顺序**：拖动卡片缩略图，首张明确标记“微信封面”。

编辑范围分成“只改这张”和“整叠统一”。背景、色板和字感默认整叠统一；文字、贴纸和涂鸦默认只改当前卡。用户可以撤销/重做最近 20 步，并随时点击“恢复这套原样”。

首版每张卡限制最多 1 个主文字层、1 个辅助文字层、6 个装饰层，避免复杂画布导致误触、性能和导出问题。画笔自由涂鸦不进入首版，先使用可变形的预制涂鸦；后续再增加用户手绘路径。

### 5.5 预览、保存与发送

- 预览页复用现有微信聊天牌堆，展示实际卡片比例和顺序；
- 每叠至少 3 张、首版最多 8 张，推荐 4–6 张；
- 保存按稳定序号执行，失败后可从未保存项继续；
- 保存完成后明确提示用户回微信按相册顺序选择全部图片，并手动勾选“发送后合并展示”；
- 不出现“一键发到微信”或“自动合并发送”的表述。

## 6. 三套候选如何自动生成

### 6.1 输入归一化

前端把用户选择整理为 `CreativeBrief`，不把界面上每个选择直接拼成提示词：

```js
{
  sourceText: '我今天想见你',
  expressionKey: 'funny-reversal',
  relationship: 'unspecified',
  intensity: 'medium',
  requestedCandidateCount: 3,
  cardRange: { min: 3, preferred: 5, max: 8 },
  locale: 'zh-CN'
}
```

`relationship` 和 `intensity` 首版不在主链路询问，使用安全默认值；未来可放进“更多偏好”。

### 6.2 先选三种策略，再调用模型

系统先从表达标签允许的策略中选出三个差异足够大的 `strategyId`，再让模型分别填充内容。这样不会出现三套结果只是同义改写。

例如“搞怪反转”固定优先组合：

```text
hard_turn + suspense_reveal + fake_checklist
```

策略选择器同时检查最近使用记录，减少连续生成相同组合。相同输入和同一候选使用固定 `seed`，保证用户进入编辑页、重新打开记录或最终渲染时布局不会随机跳动。

### 6.3 AI 只返回结构化故事计划

一次模型调用返回三个候选，不返回 Markdown，不返回最终图片：

```js
{
  candidates: [{
    candidateId: 'candidate_a',
    strategyId: 'hard_turn',
    title: '嘴硬一下',
    preservedMeaning: '今天想见对方',
    cards: [
      { order: 1, role: 'hook', text: '我今天' },
      { order: 2, role: 'misdirect', text: '不太想' },
      { order: 3, role: 'build', text: '见你' },
      { order: 4, role: 'pause', text: '……', visualCue: 'scribble-heart-hidden' },
      { order: 5, role: 'reveal', text: '才怪' },
      { order: 6, role: 'ending', text: '', visualCue: 'heart-large' }
    ]
  }]
}
```

模型适合做：语义拆句、节奏改编、策略内文案、关键词强调和装饰语义建议。模型不负责：最终中文图像、任意图层坐标、字体文件选择、微信发送、内容安全裁决和素材版权判断。

### 6.4 规则校验与自动修复

`candidateValidator` 对模型输出执行确定性检查：

- 必须正好三套且 `strategyId` 不重复；
- 每套 3–8 张，序号连续；
- 单卡主文案建议不超过 12 个中文字符，超过上限拒绝或重新拆分；
- 不允许连续两张完全相同；
- 至少包含一个 `hook`/`build` 和一个 `reveal`/`ending`；
- 模型必须声明 `preservedMeaning`；校验器检查原句中的称呼、对象、时间和核心动作没有被删除或替换，禁止无依据加入关系、地点、承诺或攻击性事实；复杂语义漂移通过固定用例和人工验收补充，不伪装成完全可靠的代码判定；
- 文字和素材键必须在渲染器支持范围内；
- 所有用户输入和模型新增文字都必须经过安全检查。

结构不合格时只允许模型修复一次；再次失败就使用对应策略的规则模板兜底，不把解析错误暴露给用户。

### 6.5 无 AI 兜底

规则模板通过槽位和短语库生成结果，例如：

```text
原句“我今天想见你”
  → 提取时间“今天”、动作“想见”、对象“你”
  → 套入 hard_turn / suspense_reveal / visual_pause
  → 仍然输出三套合法候选
```

首版规则兜底只需覆盖常见短句和无法可靠解析时的保守拆句。无法提取时间、动作或对象时，不强行理解句意：使用通用封面/停顿卡，并把用户原句完整放在 `reveal` 卡上。保守拆句优先按标点和短语分卡，绝不退回“一字一图”。

## 7. 视觉生成系统

### 7.1 场景而不是图片

候选故事计划经过 `sceneComposer` 转换为可编辑场景：

```js
{
  sceneId: 'scene_01',
  width: 1080,
  height: 1080,
  background: { assetKey: 'pink-note-02', color: '#FCE4EC' },
  layers: [
    {
      id: 'text_main',
      type: 'text',
      text: '才怪',
      effectKey: 'marker-bold',
      x: 540, y: 520, rotation: -2.1, scale: 1.04,
      color: '#F35C8C'
    },
    {
      id: 'doodle_01',
      type: 'doodle',
      assetKey: 'heart-outline',
      x: 780, y: 220, rotation: 8, scale: 0.8
    }
  ]
}
```

所有自动结果和手动编辑都只修改场景 JSON；预览和最终导出读取同一份数据。

### 7.2 字体不靠“换很多字体”制造变化

首版复用旧分支已纳入许可文件的中文马克笔字体作为基础字形，通过渲染配方形成差异：

- 按字符做小幅旋转、缩放和基线错位；
- 多次描边形成马克笔重写或粉笔断边；
- 使用颗粒遮罩、轻微墨迹缺口和高光线；
- 用彩色纸片承载单个词，形成剪贴字；
- 对关键词使用重复字影、圈画和下划线；
- 按 `seed` 固定随机参数，避免预览和导出漂移。

后续新增字体必须保留明确覆盖小程序分发、云端渲染和图片输出的许可记录。AI 可用于离线生成装饰素材草稿，但不用于运行时生成任意中文最终字形。

### 7.3 角色驱动的自动构图

场景合成器按卡片角色选择版式，而不是随机撒贴纸：

| 卡片角色 | 默认构图 |
| --- | --- |
| `hook` | 大标题偏中上，少量装饰，保证封面可读 |
| `build` | 中字号、左上或便签式排版，保持阅读节奏 |
| `misdirect` | 使用删除线、叉号、遮挡贴纸或反向箭头 |
| `pause` | 大留白、短词或纯涂鸦，形成一次呼吸 |
| `reveal` | 最大字号、强调色、爆点装饰 |
| `ending` | 图形主导或短句收尾，不堆叠信息 |

### 7.4 双渲染适配器

- 小程序端使用低分辨率 Canvas 渲染候选和编辑预览；
- 云托管使用同一场景契约输出 1080×1080 PNG；
- 两端共享布局计算、随机种子、资产键和文字换行规则；
- 小程序字体加载失败时，候选页回退为服务端低清预览，不使用系统字体冒充最终效果；
- 只有用户选中的一套生成高清 PNG，三套候选默认只生成低清预览，减少等待和传输。

## 8. 系统架构

### 8.1 总体数据流

```mermaid
flowchart LR
    A[首页示例/一句话输入] --> B[CreativeBrief 归一化]
    B --> C[输入内容安全]
    C --> D[策略选择器]
    D --> E[AI Creative Planner]
    E --> F[候选校验与一次修复]
    F -->|失败| G[规则模板兜底]
    F -->|通过| H[视觉包匹配]
    G --> H
    H --> I[Scene Composer]
    I --> J[三套低清可滑候选]
    J --> K{用户选择}
    K --> L[直接预览]
    K --> M[轻量编辑]
    M --> L
    L --> N[云端高清渲染]
    N --> O[微信牌堆预览]
    O --> P[按序保存与发送引导]
```

### 8.2 小程序模块

建议新增或重构为以下边界：

| 模块 | 单一职责 |
| --- | --- |
| `config/playRegistry.js` | 注册趣味字画及其他玩法的入口、能力和路由 |
| `config/stylePacks.js` | 视觉包、兼容背景、字感和素材白名单 |
| `config/assetRegistry.js` | 素材键、路径、尺寸、来源和版本 |
| `utils/creativeBrief.js` | 输入归一化和默认值，不包含模型调用 |
| `utils/strategySelector.js` | 选择三种差异化叙事策略 |
| `utils/candidatePlanner.js` | 调用云端规划器并处理规则兜底 |
| `utils/candidateValidator.js` | 校验候选结构和渲染能力 |
| `utils/sceneComposer.js` | 把故事计划和视觉包合成可编辑场景 |
| `utils/sceneHistory.js` | 编辑操作、撤销/重做和恢复初始状态 |
| `pages/fun-text/` | 一句话输入、表达标签和示例入口 |
| `pages/fun-text-candidates/` | 三套可滑候选和重新生成 |
| `pages/fun-text-editor/` | 有边界的卡片轻编辑 |
| `pages/template-result/` | 复用并升级为通用模板结果/渲染状态页 |
| `pages/preview/` | 继续承担接收者视角的微信叠图预览 |

页面只负责交互和状态展示，不在页面文件内硬编码故事模板、视觉包或图层计算。

### 8.3 云端模块

| 模块 | 职责 |
| --- | --- |
| `contentGuard` | 继续负责用户输入文本安全门禁 |
| `creativePlanner` 云函数 | 调用模型、要求结构化 JSON、限制策略和输出长度；不生成图片 |
| `fun-card-renderer` 云托管 | 从旧 `text-card-renderer` 演进，加载授权字体和素材，按场景批量输出 PNG |
| 云存储 | 保存短期渲染结果，沿用 24–72 小时清理策略 |

`creativePlanner` 和 `fun-card-renderer` 分开部署。前者可以更换模型而不影响渲染，后者可以增加素材和字感而不改变故事生成契约。

### 8.4 核心项目数据

```js

  playId: 'fun-text-stack',
  version: 1,
  sourceText: '我今天想见你',

  generationMode: 'ai', // ai | rules
  candidates: [{
    candidateId: 'candidate_a',
    strategyId: 'hard_turn',
    title: '嘴硬一下',
    stylePackId: 'pink-note-v1',

    originalScenes: [],
    editedScenes: []

  selectedCandidateId: 'candidate_a',
  renderStatus: 'draft',
  renderedCards: [],
  createdAt: 0,
  updatedAt: 0
}
```

本地记录保存可再次生成所需的项目规格和少量缩略图，不依赖长期有效的临时云存储 URL。

## 9. 技术路线比较与选择

### 9.1 方案 A：纯规则模板

优点是确定、便宜、离线可用、易测试；缺点是同一句话很快出现套路重复，难以持续产生“像人想出来的”三套方案。适合作为第一阶段和永久兜底，不适合作为最终唯一方案。

### 9.2 方案 B：AI 一次生成三套最终图片

优点是视觉惊喜大；缺点是中文文字错误、三套风格和角色一致性差、无法精确编辑、审核和复现困难，运行时成本与等待也更高。该方案不采用。

### 9.3 方案 C：规则 + AI 结构化规划 + 确定性渲染

该方案兼顾创意和可控性：规则决定可发送的结构和失败兜底，AI 负责文案与节奏，场景渲染器保证中文准确、预览一致和用户可编辑。它是本设计的正式方案。

## 10. 异常、降级与安全

| 情况 | 产品行为 |
| --- | --- |
| 输入为空或过长 | 阻止生成，保留输入并给出明确长度建议 |
| 输入安全检查拒绝 | 不调用模型、不渲染，提示修改原话 |
| AI 超时或不可用 | 自动切换规则模板，候选页标记“基础方案”但不中断 |
| AI JSON 不合法 | 自动修复一次；仍失败则规则兜底 |
| 三套相似度过高 | 替换重复策略并只重生成冲突候选 |
| 模型输出新增不安全文字 | 丢弃对应候选并规则重建；不把内容交给渲染器 |
| 预览字体加载失败 | 请求服务端低清预览，不使用系统字体代替 |
| 可选贴纸资源丢失 | 移除该装饰并保持文字卡可用，同时记录资产错误 |
| 主背景或字体资源丢失 | 阻止高清导出，保留项目并允许重试 |
| 单张高清渲染失败 | 整叠不写入完成状态，显示失败卡并支持继续重试 |
| 相册保存部分失败 | 显示已保存/未保存数量，从失败项继续 |
| 微信版本不支持合并展示 | 结果仍可作为普通图片保存，发送引导说明降级 |

所有用户输入先过 `contentGuard`；模型输出在进入场景合成前再次执行规则和内容安全检查。生产环境审核服务异常时不绕过审核。

用户首次使用 AI 创意规划前，页面以短说明告知文字会发送到云端用于本次方案生成；不把原文用于公开模板或跨用户训练数据。项目规格保存在设备本地，云端输入、低清预览和高清结果沿用 24–72 小时临时清理策略。AI 上线仍以个人/企业主体和生成式能力审核范围明确为前提；范围未明确时只发布规则阶段。

## 11. 性能与成本控制

- 三套候选使用一次结构化模型调用，不为每套单独发起请求；
- 候选阶段只传 JSON 和低清预览，不提前渲染三套共十几张高清 PNG；
- 只有用户选中的方案进入高清渲染；
- 视觉资产使用版本号和本地缓存，避免重复下载；
- 内置示例以 `sourceText + brief + strategySet + contentVersion` 计算共享缓存键；用户输入只允许在当前项目内复用，不用原文哈希跨用户共享缓存；
- 每个候选固定种子，编辑、重开记录和导出不重新随机；
- 模型调用设置明确超时，超时直接规则兜底，不让用户无限等待。

## 12. 与现有实现的替换与复用

### 12.1 保留

- `contentGuard` 文本安全门禁；
- 微信叠图 `pages/preview`；
- 顺序保存、相册授权处理和发送引导；
- `template-result` 的批量任务与记录思路；
- 旧云托管中的字体注册、PNG 上传、失败清理和许可文件；
- 旧马克笔渲染的颗粒、偏移、旋转和程序化贴纸算法，重构后作为一个字感/素材包。

### 12.2 替换

| 旧模块/规则 | 新模块/规则 |
| --- | --- |
| `pages/bigtext/` 输入 + 三主题 | `pages/fun-text/` 一句话 + 组合表达标签 |
| `buildCardSpecs` 按字符拆卡 | `candidatePlanner` 按策略生成 3–8 张故事卡 |
| 一次只生成一套 | `fun-text-candidates` 同时比较三套可滑方案 |
| `THEMES` 固定主题 | `stylePacks + assetRegistry` 兼容视觉包 |
| `buildMarkerCardStyle` 随机单字样式 | `sceneComposer` 角色驱动构图和确定性种子 |
| `text-card-renderer /render` | `fun-card-renderer /render-stack` 场景批量渲染 |
| 贴纸只能自动出现 | 自动推荐 + 用户轻量移动/缩放/旋转/删除 |
| 记录类型 `bigtext` | 新记录类型 `funtext`，旧类型只保留兼容读取 |

### 12.3 不直接合并旧功能分支

实施时不把 `codex/bigtext-handwrite` 整分支直接合入主线，因为其中页面流程和任务模型已经被替代。应按新实施计划选择性迁移测试通过的渲染、授权字体、贴纸和服务错误处理代码，并为新场景契约重新编写测试。

## 13. 分阶段实施路径

四个阶段分别编写实施计划和完成验收，不把整套功能塞进一次代码改动。用户确认本设计后，下一份实施计划只覆盖阶段 1；阶段 2–4 均在前一阶段真机闭环成立后再单独确认。

### 阶段 1：无 AI 的完整骨架

范围：建立 `fun-text-stack` 注册项、四个规则策略、三个视觉包、场景数据模型、三套候选页、选中后预览/高清渲染/保存全链路。轻编辑只提供改单卡文字、整叠换视觉包和调顺序。

目的：先验证“输入一句话 → 三套候选 → 真机发送”这个产品闭环，不让模型接入掩盖结构问题。

### 阶段 2：AI 创意规划

范围：新增 `creativePlanner`、结构化输出、候选校验、相似度约束、一次修复和规则兜底。三套策略仍由本地先选，AI 不能自由发明不可渲染结构。

目的：让同一句话出现更自然的语义拆分和不同表达，同时保持全链路可测试。该阶段只有在 P0 已明确小程序主体、生成式能力审核范围、隐私说明和失败口径后才进入可发布范围；此前可以保留在开发/体验环境。

### 阶段 3：轻量定制

范围：背景变体、字感切换、贴纸/涂鸦添加、移动/缩放/旋转/删除、单卡/整叠作用域、撤销/重做和恢复原样。

目的：给用户足够的参与感，但不暴露通用编辑器参数。

### 阶段 4：智能改款与内容扩展

范围：增加“更可爱”“更离谱”“再短一点”等一键变体；开放更多表达标签、视觉包、贴纸和涂鸦；评估用户自由手绘路径。

目的：把可玩性扩展建立在已稳定的场景模型和编辑器上，而不是继续增加互不相干的页面。

## 14. 测试与验收

### 14.1 自动化测试

- `CreativeBrief` 归一化、长度和默认值；
- 策略选择差异性、最近使用去重和固定种子；
- 三候选结构、卡片角色、文字长度和原意保留规则；
- AI 合法响应、非法 JSON、超时、相似候选和规则兜底；
- 视觉包与素材注册表完整性、许可元数据和资源存在性；
- 场景合成确定性、图层上限、单卡/整叠编辑作用域；
- 撤销、重做、恢复原样和记录重开；
- 高清渲染批次、失败清理、重试和输出顺序；
- 预览、保存、授权拒绝和部分失败续存回归；
- 旧 `bigtext` 记录兼容读取或明确不可重开的提示。

### 14.2 视觉回归

为每个“策略 × 视觉包 × 卡片角色”保留固定种子的黄金图。变更渲染器、字体、换行或资产时生成对比图，人工检查：

- 中文没有缺字、裁切或错误换行；
- 封面在微信牌堆尺寸下仍可读；
- 三套候选确有不同视觉层次；
- 贴纸不遮挡主文案；
- 预览和 1080 PNG 的主要位置一致。

### 14.3 真机验收

- iOS 与 Android 各完成首页示例、一句话生成、三套候选、编辑、保存和历史重开；
- 分别测试 3、5、8 张卡；
- AI 正常、AI 关闭、审核拒绝、渲染失败和部分保存失败路径；
- 回微信按引导发送，核对封面、顺序、左右滑动、展开/收起和普通图片降级；
- 记录实际字体加载、候选首屏时间、高清渲染时间和保存结果，不能用模拟器代替真机结论。

完成前仍执行 `docs/governance.md` 规定的完整检查。

## 15. 已确认的产品取舍

本设计已采用以下默认取舍，用户确认设计即视为同意：

1. 用户功能名使用「趣味字画」，内部 ID 使用 `fun-text-stack`；
2. 首屏不要求分别选择情绪、玩法、字体和背景，只提供一个可跳过的组合表达标签；
3. 默认一次生成三套候选，每套 3–8 张；
4. 首版先做规则闭环，再接 AI，不把 AI 作为可用前提；
5. 阶段一不开放贴纸/涂鸦手动编辑；阶段三再开放预制素材的移动、缩放、旋转和删除，自由画笔继续后置；
6. 旧大字滑卡分支不整体合并，只选择性迁移可复用代码；
7. 阶段一先形成逐文件、逐测试的实施计划，用户选择执行方式后再开始改业务代码。
