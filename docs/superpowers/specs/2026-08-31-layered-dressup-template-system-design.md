# 分层云换装与内置模板系统设计说明

**日期：** 2026-08-31
**状态：** 用户已于 2026-08-31 确认，进入实施
**目标版本：** 下一阶段旗舰玩法
**参考玩法：** [小红书「微信叠图新功能」示例](https://www.xiaohongshu.com/discovery/item/6a2fc418000000000f01e563)

> **后续路线说明（2026-08-31）：** 本文的分层云换装范围不变；其中对“大字滑卡留在实验室”的安排已被后续「趣味字画」设计替代。最新跨功能顺序以 `docs/roadmap.md` 为准，文字玩法设计见 `2026-08-31-fun-text-stack-design.md`。

## 1. 设计结论

WePicTool 下一阶段不继续扩张成一组彼此独立的小工具，而是先把首页旗舰能力升级为「分层云换装」：把头像/发型、上衣、下装、鞋子分别做成一叠图片，用户在微信聊天中独立左右滑动四叠图片，自由组合造型。

首版同时支持两种素材来源：

1. 使用产品内置素材包，一键生成完整示例，让第一次打开的用户立即理解玩法。
2. 上传自己的素材，按部位分组并生成自己的换装叠图。

两种来源允许混用。例如用户上传自己的上衣和下装，同时使用系统的头像与鞋子。该功能不做真实 AI 试穿，也不承诺小程序直接把多张图片发送到聊天；产品负责生成、预览、按顺序保存，并指导用户回微信合并发送。

## 2. 问题与机会

当前「穿搭叠图」已具备选图、AI 分类、抠图、白底卡片、分组预览、顺序保存和发送引导，但产品表达仍偏向“图片处理工具”。首页其余入口大多是未上线占位，用户难以在打开后立即看到微信叠图真正有趣的结果。

参考玩法的关键不在于生成一张完整穿搭图，而在于：

- 微信聊天里纵向排列多叠图片；
- 每一叠代表一个独立部位；
- 每个部位都能单独滑动；
- 四个部位叠加为“纸娃娃式”自由换装；
- 收图人可以边滑边组合，而不是只看制作者预先配好的套装。

因此，现有「成套搭配」和「滑滑换装」不再作为两个相近的独立入口，统一并入「分层云换装」。

## 3. 目标与非目标

### 3.1 目标

- 用户不上传图片也能通过内置素材包完整试玩。
- 用户可以制作自己的头像/发型、上衣、下装、鞋子四组换装素材。
- 用户可以在自己的素材和系统素材之间自由补充、替换和混用。
- 小程序内的预览要明确呈现四叠图片独立滑动的效果。
- 每组输出顺序稳定，保存后能被用户按清晰步骤发到微信。
- 玩法、素材包、卡片渲染、预览和保存能力形成可复用底座，后续可承载胶片相册、前后对比、全景画卷等玩法。

### 3.2 非目标

- 不做把衣服真实穿到真人身上的 AI 虚拟试衣。
- 不做人体重建、姿态迁移、体型推断或完整人物合成。
- 不保证微信聊天中的最终排版像素级一致；微信客户端版本和发送选择由用户控制。
- 不做复杂画布编辑器、自由拖拽变形或 Photoshop 式精修。
- 不做模板商城、付费、账号体系和云端长期同步。
- 不直接复刻第三方素材；内置素材仅使用自制、AI 生成且权利清晰、或明确授权的资源。

## 4. 用户看到的产品结构

### 4.1 首页信息架构

首页从当前“一个主功能 + 多个即将上线占位卡”调整为五层：

1. **品牌说明**：一句话说明“把素材做成微信里可以滑着玩的叠图”。
2. **真实效果演示**：直接展示四个部位独立滑动的短演示或交互预览。
3. **旗舰入口：分层云换装**：两个主按钮「直接试玩」和「上传自己的素材」。
4. **热门模板**：展示可直接使用的素材包，而不是重复展示功能名。
5. **更多玩法与工具**：只突出已可用和下一项将实现的能力，其余进入实验室或暂不展示。

首页功能分区确定为：

| 分区 | 功能 | 定位 |
| --- | --- | --- |
| 旗舰玩法 | 分层云换装 | 当前优先实现的核心体验 |
| 照片玩法 | 胶片相册、前后对比、无缝画卷 | 复用图片输入与卡片输出底座 |
| 节奏玩法 | 内置翻页动画、剧情反转 | 依赖模板序列与顺序预览 |
| 群聊互动 | 盲盒抽签 | 后续纯前端玩法 |
| 实用工具 | 资料打包 | 后续多批选图与分组工具 |
| 文字玩法 | 趣味字画 | 替代大字滑卡，按独立设计在分层换装之后实施 |
| 实验室 | 拼图揭秘 | 保留探索结果，不占首页主叙事 |

### 4.2 模块与模板的区别

- **玩法模块**定义用户要完成的任务和工作流，例如「分层云换装」或「胶片相册」。
- **模板/素材包**定义同一玩法内可直接使用的内容和视觉，例如「抽象搞怪」「日常基础」「甜酷少女」。

首页可以高频更新模板，但不需要不断增加顶层功能入口。一个模板必须归属于一个玩法模块。

## 5. 分层云换装交互设计

### 5.1 四个标准部位

首版固定四组，避免用户理解成本和任意分组导致的排版失控：

| 组 | 标识 | 推荐数量 | 内容 |
| --- | --- | --- | --- |
| 头像/发型 | `head` | 3–8 | 头像、发型、帽子或头部造型 |
| 上衣 | `tops` | 3–12 | 上装、连衣裙的上半身表达 |
| 下装 | `bottoms` | 3–12 | 裤装、裙装或下半身造型 |
| 鞋子 | `shoes` | 3–8 | 鞋履或脚部造型 |

每组 12 张是首版产品上限。用户可分批选择素材，但单次系统图片选择仍遵循微信接口限制。

### 5.2 三条进入路径

#### 路径 A：直接试玩

```text
首页点击「直接试玩」
  → 选择一个内置素材包，默认首包可直接进入
  → 自动建立四个完整分组
  → 进入四叠联动预览
  → 按组保存
  → 查看微信发送顺序引导
```

该路径使用已预生成的成品卡，不触发 AI、不要求相册权限，也不产生等待时间。它承担产品教学和效果证明。

#### 路径 B：上传自己的素材

```text
首页点击「上传自己的素材」
  → 逐组选图，或一次选图后智能建议分组
  → 确认/修改所属部位
  → 可选智能去背与白底整理
  → 补齐不足 3 张的组，或跳过该组
  → 调整顺序与标签模式
  → 四叠联动预览
  → 按组保存并查看发送引导
```

用户可直接按组上传，从而在没有 AI 或 AI 失败时仍能完成。现有 AI 分类只作为加速器，不作为可用性的前提。

#### 路径 C：混合素材

用户在任一分组中点击「添加素材」，可在「我的图片」和「系统素材」之间选择。系统素材加入项目后与用户素材遵循同样的排序、删除、预览和保存规则。

### 5.3 分组不足 3 张的处理

微信叠图需要每组至少 3 张。对换装玩法，不使用封面卡、教程卡或空白卡硬凑数量，因为这些卡会在滑动中破坏部位组合。

每个不足 3 张的组只提供三种操作：

1. 继续上传自己的素材；
2. 从系统素材中补齐；
3. 暂时跳过该组，不保存也不发送这一叠。

只要至少一个分组达到 3 张，用户可以继续导出；界面需清楚说明未达标分组不会形成微信叠图。内置试玩包的四组必须全部不少于 3 张。

### 5.4 标签模式

提供两种输出模式：

- **自由换装**：默认不显示编号，视觉更接近纸娃娃和参考视频。
- **帮我挑选**：显示轻量组名与编号，便于朋友回复“上衣 2 + 下装 3”。

标签是渲染参数，不修改原始素材；切换后只重新合成卡片，不重新调用 AI。

### 5.5 排序与删除

- 每组素材可删除。
- 每组素材可长按拖动排序。
- 第一张是微信中该叠的初始封面，因此排序界面要突出“首图”标记。
- 删除后若某组降至 2 张，立即变为不可叠图状态，但不丢弃已有编辑。
- 系统素材与用户素材采用相同的排序规则。

### 5.6 四叠联动预览

预览页纵向展示头像/发型、上衣、下装、鞋子四个独立牌堆。每叠可以独立左右滑动，顶部显示当前组合摘要；不足 3 张或被跳过的组显示占位说明，但不伪装成可发送叠图。

该预览复用现有微信叠图牌堆的折叠、滑动、展开能力，但增加多实例同屏规则：

- 四叠各自维护当前索引和手势状态；
- 横向手势只控制当前部位，纵向手势仍用于页面滚动；
- 切换一组不会重置其他三组；
- 预览用于说明玩法，不承诺代替微信真实聊天验收。

### 5.7 保存与发送引导

输出按有效组分别保存，顺序固定为：头像/发型 → 上衣 → 下装 → 鞋子。每组文件保持稳定的组前缀和两位序号，确保相册中容易辨认和选择。

保存完成后展示四步引导：

1. 回到目标微信聊天；
2. 每次只选择一个部位组的全部图片；
3. 勾选「发送后合并展示」并按组发送；
4. 按头像/发型、上衣、下装、鞋子的顺序发送四叠。

产品不出现“一键发到微信”的误导性承诺。

## 6. 内置模板与素材系统

### 6.1 当前内置案例

2026-09-06 用户用 16 张项目自有图片替换旧案例。当前默认素材包包含四套完整造型，每套依次对应头像/发型、上衣、下装和鞋子：

1. 男生短发、白色短袖、蓝色牛仔裤、白色板鞋；
2. 女生长发、米白针织衫、灰色长裙、棕色短靴；
3. 男生短发、卡其外套、深灰工装裤、灰白运动鞋；
4. 女生短发、浅蓝上衣、白色长裙、白色凉鞋。

首页与工作台按部位展示四张图片，同一序号始终代表同一套完整搭配，用户也可跨序号自由混搭。高清源文件不进入小程序主包；运行素材统一压缩为最长边 640 px 的 JPEG，并保持头像方图、衣物 3:4 竖图和项目自有授权标记。

### 6.2 素材来源规则

内置素材只允许以下来源：

- 项目自行绘制或拍摄；
- 使用 AI 生成，并保留生成记录和使用权说明；
- 来自许可明确且允许在小程序中再分发的素材。

不直接下载、裁剪或重绘小红书作者、品牌商品图、明星照片、游戏角色或其他第三方受保护素材。参考内容只用于理解交互，不作为素材来源。

### 6.3 注册表模型

玩法与素材分成两个注册表，避免把首页文案、业务流程和资源路径硬编码在页面中。

```js
// 玩法定义
{
  id: 'layered-dressup',
  version: 1,
  title: '分层云换装',
  status: 'available',
  entryModes: ['demo', 'upload', 'mixed'],
  groupSchema: ['head', 'tops', 'bottoms', 'shoes'],
  renderer: 'layered-card',
  preview: 'multi-stack',
  exporter: 'grouped-sequence'
}

// 素材包定义
{
  id: 'funny-paper-doll-v1',
  playId: 'layered-dressup',
  version: 2,
  title: '四套基础穿搭',
  cover: '...',
  license: 'project-owned',
  groups: {
    head: [],
    tops: [],
    bottoms: [],
    shoes: []
  }
}
```

素材包元数据随小程序发布；大图资源使用可缓存的云存储/CDN 地址，避免首包体积失控。每个素材项记录尺寸、推荐锚点、缩放、资源版本和来源类型。

## 7. 项目数据模型

分层换装项目不直接复用当前 `outfit` 任务对象的三组假设，而是在共享能力上增加新的玩法项目契约：

```js
{
  projectId: 'project_xxx',
  playId: 'layered-dressup',
  sourceMode: 'demo', // demo | upload | mixed
  templateId: 'funny-paper-doll-v1',
  ratio: '4:5',
  labelMode: 'clean', // clean | numbered
  groups: {
    head: [],
    tops: [],
    bottoms: [],
    shoes: []
  },
  sendability: {},
  createdAt: 0,
  updatedAt: 0
}
```

每个素材项至少包含：稳定 ID、所属组、来源（用户/系统）、原图地址、合成图地址、排序值、处理状态、是否已去背、渲染参数和错误信息。项目保存到本地记录；用户云端临时文件继续遵循 24–72 小时清理策略。

## 8. 技术边界与复用关系

### 8.1 直接复用

| 已有能力 | 分层云换装中的用途 |
| --- | --- |
| 图片选择、压缩与上传 | 用户素材输入 |
| `processOutfit` 分类与抠图 | 上衣/下装/鞋子智能建议和可选去背 |
| `cardComposer.js` | 统一画布、白底、锚点、编号渲染 |
| 结果分组与发送能力校验 | 每组不少于 3 张判断 |
| 微信叠图预览 | 改造成四个独立实例的联动预览 |
| 顺序保存与授权处理 | 按组导出 |
| 本地记录 | 保存项目摘要并再次打开 |
| 内容安全能力 | 用户输入文字与需要上传处理的素材门禁 |

### 8.2 必须新增或重构

- 玩法注册表和素材包注册表；
- 首页的玩法/模板数据驱动渲染；
- `head` 分组及其卡片锚点；
- 按组添加用户素材或系统素材的编辑页；
- 组内删除、拖动排序和首图标记；
- 四叠独立状态的预览适配器；
- 清爽/编号两种标签渲染模式；
- 项目级本地记录和素材包版本信息；
- 按四组保存和发送引导。

### 8.3 AI 能做与不能做的部分

AI 适合承担：

- 建议上衣、下装、鞋子的分组；
- 去背、白底整理和质量异常提示；
- 离线生成权利清晰的内置素材草稿；
- 后续为剧情、标题和模板变体生成候选内容。

AI 不应承担：

- 控制微信最终的合并发送、封面和滑动状态；
- 保证任意真人照片都能被拆成可组合的头、上衣、下装和鞋；
- 用单张平面商品图生成准确的真人试穿效果；
- 自动解决第三方素材版权；
- 在模型失败时阻断手动制作路径。

因此首版工作流是“模板和手动分组先成立，AI 作为增强”，而不是“必须 AI 成功才能使用”。

## 9. 异常与降级

| 情况 | 产品行为 |
| --- | --- |
| AI 分类失败 | 素材保留在待分组区，用户手动归组 |
| AI 去背失败 | 保留原图并允许直接做卡，提示可重试 |
| 某组不足 3 张 | 提示上传、系统补齐或跳过，不生成干扰卡 |
| 素材包资源下载失败 | 重试单个资源；不可用组不进入保存队列 |
| 单张卡片合成失败 | 其他卡继续生成，失败项可重试 |
| 相册授权拒绝 | 复用现有授权设置引导，不丢失项目 |
| 批量保存中断 | 显示已保存/失败数量，可从失败项继续 |
| 低版本微信不支持预期展示 | 明示降级为普通图片发送，生成结果仍可保存 |

## 10. 隐私、内容安全与资源体积

- 直接试玩只读取系统素材，不上传用户数据。
- 用户素材若选择 AI 分类或去背，上传前说明用途和 24–72 小时临时清理规则。
- 用户跳过 AI 时，能在本地完成的卡片合成不应强制上传。
- 用户输入的标题或自定义标签经过现有文本安全检查。
- 需要云端 AI 处理的图片继续经过现有图片安全门禁。
- 内置素材保留来源与版本记录，删除权利链不清楚的资源。
- 首包只内置缩略图和必要的轻量资源；成品大图按需下载并缓存。

## 12. 实现优先级与阶段验收

### P0：分层云换装可用闭环

范围：完成删除、排序、四组项目模型、用户按组上传、手动分组、四叠预览、按组保存和发送引导；复用现有 AI 分类与去背，但 AI 失败不阻断。

验收：用户只使用自己的素材，至少能完成三个有效分组的制作、独立滑动预览、按正确顺序保存和微信真机发送；首图、删除、排序和不足 3 张状态正确。

### P1：内置模板与混用系统

范围：建立玩法/素材注册表，上线四套完整基础穿搭案例；支持直接试玩和任一组混合系统素材。后续是否增加独立风格包按真实使用反馈决定。

验收：新用户不授权相册即可从首页在短路径内看到四叠预览并保存；三套素材包结构合法、四组完整、来源记录清楚；混合项目再次打开不丢失来源和顺序。

### P2：照片类高复用玩法

按顺序实现：胶片相册 → 前后对比 → 无缝画卷。三者复用玩法注册表、图片输入、卡片渲染、预览、保存和发送引导，不引入新的 AI 强依赖。

验收：每个新玩法只增加自己的输入规则与渲染器，共享能力不复制到独立页面逻辑中。

### P3：节奏与故事玩法

按顺序实现：内置翻页动画 → 剧情反转 → 自定义 GIF/短视频抽帧。先使用预生成帧素材验证滑动节奏，再评估云托管 `ffmpeg` 的耗时、体积和兼容性。

### P4：其余玩法与实验

盲盒抽签、资料打包和拼图揭秘按兴趣继续。文字方向不再恢复旧大字滑卡，统一转入「趣味字画」设计；授权字体仍是可复用技术资产，但不再把获得更多字体作为产品启动条件。

## 13. 测试与真机验证口径

实施时至少覆盖：

- 注册表结构、素材包完整性和每组最少数量的单元测试；
- 用户素材、系统素材、混合素材三种项目状态测试；
- 删除后降级、排序后首图和导出序号测试；
- AI 分类/去背失败仍可手动完成的测试；
- 四个预览实例互不重置、横纵手势不冲突的交互测试；
- 顺序保存的成功、部分失败、授权拒绝和续存测试；
- iOS 与 Android 真机分别完成内置试玩、用户上传和微信发送；
- 微信中逐项核对四叠顺序、封面、独立滑动、展开/收起和普通发送降级。

自动化检查仍以 `docs/governance.md` 规定的完整命令为准。真机结论记录在对应迭代日志，不能由模拟器预览代替。
