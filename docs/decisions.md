# WePicTool 关键决策记录

## 2026-09-06：首页换装预览使用手势驱动的单图循环，不做定时轮播

**背景：** 首页每个部位同时显示三张小图时，素材难以辨认，右侧 2×2 摘要也不容易对应穿搭顺序。用户要求放大图片并自然切换；“自动切换”若实现为定时轮播，会在用户查看或准备点击时擅自改变当前搭配。

**决定：** 头像/发型、上衣、下装、鞋子四行各使用一个原生循环 swiper，静止时只显示当前一张放大素材；切换只由横向手势或左右箭头触发。右侧按四部位顺序竖向显示当前选择。AI 穿搭整理入口同时改为先进入空选图状态，只有点击添加时才申请相册动作；返回首页和清空重选保持不同语义。

**影响：** 首页分层预览卡允许增高并纵向滚动，优先保证图片识别和部位对应，不再坚持全部预览进入首屏。AI 处理、分层素材页、统一导出和保存协议不变；真实跟手效果、相册授权与双端尺寸仍必须在真机验收。

## 2026-09-05：趣味字画扩展采用白名单内容库与聚焦编辑

**背景：** 只有一句话输入和少量整组编辑时，用户既不容易找到可玩的内容，也很难修正某一张卡片；直接演化成通用修图器又会增加学习成本、不可读配色、渲染协议和包体风险。

**决定：** 首轮交付 6 类 12 个结构化案例、8 种规则叙事玩法、7 套视觉包和 3 种 OFL 字体字感；编辑器固定为「内容 / 样式 / 装饰」三入口，只开放成套背景/配色、字号档位、白名单装饰手势、20 步撤销重做和恢复。用户照片、任意颜色、任意字体、滤镜、抠图、自由画笔和无限图层不进入本轮。新增场景字段以 version 1 的可选附加字段兼容旧记录，字体不可用时不静默回退系统字体。

**影响：** 小程序与云端 renderer 必须共享同一组风格、配色、字体和素材键；有效编辑会使旧渲染、manifest 与续存状态失效。三款字体仅随云端 renderer 分发，小程序通过白名单字体端点按需加载，避免重现主包超过 2 MiB。阶段 C 的用户照片能力必须重新设计、确认和安全验收。

## 2026-09-05：首页按任务选择，共用单一主预览

**背景：** 当前首页把分层换装演示、趣味字画演示、旗舰入口、热门模板、工具和教程纵向堆叠，同一玩法重复出现；四叠演示还使用没有内容的白色装饰卡表达“后面有图”，真机上表现为模糊空白块。用户需要长距离滚动才能看到其他功能和真正的开始入口。

**决定：** 首页先问“今天想做什么？”，并排展示分层换装和趣味字画；两个玩法共用一个主预览位置，切换时保留各自索引。当前玩法的双操作紧跟预览，完整教程移到预览/保存阶段按上下文展示。可滑动性只用真实相邻素材、序号和箭头表达，不再绘制空白叠卡。

**影响：** 旧旗舰卡、热门模板和首页长教程被移除；AI 穿搭整理保留为次级真实入口，未实现工具只能明确显示“即将上线”。本决定只改变首页发现与开始路径，不改变各玩法编辑、预览、保存、记录或云端契约。

## 2026-09-04：顺序识别依赖图片内可见角标，不依赖相册文件名

**背景：** `wx.saveImageToPhotosAlbum` 只接收本地 `filePath`，不能指定目标文件名或系统相册/微信图片选择器的排序。旧玩法手册把“01、02 文件名控制顺序”写成保证，超出了小程序可控边界。

**决定：** 三种已接入玩法共用版本化 export manifest；每叠独立从 `01` 编号，使用独立 Canvas 把两位角标写入最终图片，预览和保存复用同一 `exportUrl`。保存严格串行并按 manifest 指纹续存；发送引导要求每次只发送一叠、按角标选择并确认 `01` 在第一位。

**影响：** 系统相册实际排列和微信勾选顺序仍需用户确认，产品不承诺自动排序或一键直发。图片角标是导出装饰层，不进入玩法 scene JSON、远端渲染指纹或长期记录缓存；开发者工具、双端真机和真实微信聊天仍是 P0 完成条件。

## 2026-08-31：趣味字画替代大字滑卡

**背景：** 旧大字滑卡已经验证授权字体、马克笔颗粒、程序化贴纸、云端 PNG 和叠图导出，但“一字一图 + 固定主题”缺乏真实聊天语境、叙事节奏和用户可玩性。继续增加字体和背景会把产品推向通用图片编辑器，仍然不能形成微信叠图专属价值。

**决定：** 用户侧功能改为「趣味字画」：输入一句话和一个可跳过的组合表达标签，系统自动生成三套不同叙事策略的可滑候选；选中后可直接保存或轻量修改文字、背景、字感、贴纸、涂鸦和顺序。旧 `bigtext` 产品流程不再进入主线，分支只作为可复用技术来源。

**影响：** 首页、路线图、玩法手册和未来记录类型使用 `fun-text-stack` / `funtext`；旧大字滑卡设计标记为历史。实施前仍需用户确认新设计并编写独立实施计划。

## 2026-08-31：创意规划与最终图片生成解耦

**背景：** 纯规则模板稳定但容易重复；让图像模型一次生成带中文的最终卡片会产生错字、风格漂移、不可编辑和难以复现的问题。

**决定：** 趣味字画采用“规则策略 + AI 结构化故事计划 + 确定性场景渲染”。AI 只负责拆句、节奏和候选文案；策略选择、内容安全、卡数、角色、素材兼容和最终 PNG 由确定性代码控制。AI 失败时规则模板必须完成全链路。

**影响：** 新增候选校验、场景 JSON、小程序低清预览和云托管高清渲染边界；不采用运行时 AI 最终中文生图，不把模型成功作为功能可用前提。

## 2026-07-26：README 同步必须留下可检查的决定

**背景：** README 在文档整理时已被人工更新，但原有规则没有要求后续合并新功能、修改运行或部署方式时必须判断 README 是否需要同步；自动检查也无法发现遗漏。

**决定：** 对产品改动和文档结构变动，当天迭代日志必须写明“README 已更新：原因”或“README 无需更新：原因”。前者必须随提交包含 `README.md`；检查器负责验证这项记录和暂存关系。

**影响：** 以后合并大字滑卡等用户可感知功能时，不能只更新当前状态和迭代日志；必须同时更新 README，或清楚记录为什么无需更新。

## 2026-07-26：当前文档与历史资料分层

**背景：** 原有 `docs/product/` 混放当前状态、开发指南、长期规格和历史归档；部分入口还指向已过期的阶段与模型信息，容易让新会话或开发工具读到错误结论。

**决定：** 当前工作只以 `docs/current.md`、`docs/roadmap.md`、`docs/governance.md`、产品规格和当前 AI 提示词为依据。旧项目状态、旧归档与已结束 AI 调研统一放入 `docs/history/`；`docs/superpowers/` 继续保留设计和实施证据，并由索引明确其历史属性。重复且链接失效的开发指南删除。

**影响：** 日常开发不再维护多个“当前状态”文件；需要追溯旧选择时仍可从历史资料和 Git 记录中找到来源。

## 2026-07-18：定位为微信叠图玩法生成器

**背景：** 产品不再只服务穿搭白底卡，需要形成可扩展的图片叠图玩法库。

**决定：** 穿搭白底卡是旗舰能力；新玩法遵循“输入 → 卡片生成 → 叠图预览 → 按序保存 → 发送引导”的统一管线。

**影响：** 玩法模板应优先复用保存、预览和记录能力，不发展为通用表情包或复杂编辑器。

## 2026-07-26：大字滑卡暂不接入 AI 或自建字库

> **状态：** 该产品路线已被 2026-08-31「趣味字画替代大字滑卡」决定取代；字体授权和“不用 AI 生成最终中文文字图”的技术边界继续有效。

**背景：** 目标是真实手写质感，但当前没有自有数千字素材，也没有明确可用于小程序云端渲染的完整商业字体授权。

**决定：** 保留当前大字滑卡分支成果，暂停字体视觉迭代；后续取得授权完整字体或定制字库后再继续。

**影响：** 不使用手机主题字体包、不从参考截图提取字形、不以 AI 生成任意中文最终文字卡。

## 2026-07-26：上线范围先于新增 AI 能力

**背景：** 个人主体小程序收到与 AI/深度合成相关的审核限制提示。

**决定：** 先明确企业主体申请或非 AI 上线版本，再决定是否扩展 AI 穿搭能力。

**影响：** 近期优先真机验收、模板入口和非 AI 照片滑卡，不新增 AI 生图能力。
