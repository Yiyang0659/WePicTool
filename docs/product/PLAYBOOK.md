## 1. 平台事实（复刻效果的物理基础）

以下每条都是**已核实的微信平台行为**（核实日期 2026-07-18），是所有玩法设计的前提，不随我们的实现改变：

| # | 平台事实 |
| --- | --- |
| 1 | 在微信聊天中发送 **3 张及以上** 图片/视频时，发送面板出现「发送后合并展示」选项，**需用户手动勾选**，默认不勾选。 |
| 2 | 合并发送后以**折叠卡片**展示：有封面、可左右滑动预览、可点击展开/收起。 |
| 3 | 支持**一键保存全部**、**整体转发**。 |
| 4 | 单次最多发 **99 张**。 |
| 5 | **视频可混入叠图**（15 秒内小视频，或相册 5 分钟内视频）。 |
| 6 | 合并展示仅 **iOS / Android 生效**，电脑端仍逐张显示；无漏看提醒。 |

### 1.1 关键推论：卡片内容和可识别顺序是工具能设计的东西

- 叠图的**封面**和**滑动顺序**由用户在微信里的**勾选顺序**决定，小程序无法控制微信侧行为。
- 因此工具能设计的是：**每张卡的内容**、**图片内可见编号（01、02……）**、串行保存过程和发送引导；系统相册与微信选择器的实际排列不可控。
- 推论：最终图片必须带可见编号，发送引导必须教用户每次只发送一叠、按图片角标勾选并确认 `01` 在第一位。`wx.saveImageToPhotosAlbum` 不能指定目标文件名或相册排序，不能把文件名写成顺序保证。

### 1.2 ≥3 张硬约束

- 不足 3 张不触发「发送后合并展示」选项，玩法整体不成立。
- **所有准备发送为叠图的输出必须至少 3 张**；不足时按玩法选择补真实素材、补设计内卡片、降级为普通发送或跳过，不能静默伪装为可合并展示。

## 2. 产品定位与红线

### 2.1 定位

微信「合并发送 / 叠图」玩法生成器——**穿搭叠图与趣味字画是当前两条主玩法；AI 整理是穿搭工作台中的可选添加方式，玩法模板库是长期资产**。

> 一叠图 = 有封面、有顺序、有节奏、可整体流通的图组。

- 不做衣橱管理，不做通用表情包工具。
- 核心资产 = **玩法模板库** + **对叠图交互细节的理解**（封面、顺序、节奏、展开双形态）。

### 2.2 红线

1. 所有新玩法必须走**统一叠图管线**（第 3 章），不做独立形态的功能。
2. 整蛊类玩法只做**可爱反转**，不做恐怖惊吓内容，避免投诉与审核风险。
3. 用户输入文字必须过 `msgSecCheck` **内容安全检测**。
4. 结果图**不加水印**。
5. **每叠最少 3 张卡**。是否允许补卡由玩法定义：穿搭叠图不得用无关卡硬凑，只能补真实素材或跳过；文字/剧情玩法可用设计内的封面或节奏卡补足。任何不足都必须明确提示。

## 3. 统一叠图管线

所有模块共享同一条 5 段主管线。新玩法 = 注册玩法 + 新增输入器和卡片生成器，后半段全部复用：

```text
输入器（选图 / 文字 / 模板参数）
  → 卡片生成器（前端 Canvas 为主）
  → 叠图预览（复用 pages/preview 微信聊天预览页）
  → 编号保存（图片内写入 01、02……，按 manifest 串行保存并支持断点续存）
  → 发送引导（教用户按编号勾选 + 勾选「发送后合并展示」）
```

回流引导卡和统一埋点是后续增强，不是当前已实现主管线的一部分。

### 3.0 用户交互主流程图

```mermaid

    A[打开 WePicTool] --> B{今天想做什么}
    B -->|主玩法| C[穿搭叠图<br/>内置试玩 / 用我的图片]
    B -->|主玩法| D[趣味字画<br/>示例 / 输入一句话]
    C --> E{添加素材方式}
    E -->|自己分层| F[四部位直接添加]
    E -->|AI 帮我整理| O[选 1-9 张<br/>分类去背后复核]
    O --> F
    D --> F
    F --> G[卡片生成器: 前端 Canvas 为主<br/>穿搭走云函数分类 + 抠图]
    G --> H{≥3 张卡?}
    H -->|不足| I[按玩法补真实素材 / 设计内卡片<br/>或降级 / 跳过]
    H -->|满足| J[叠图预览<br/>pages/preview 模拟微信聊天]
    I --> J
    J --> K[编号保存到相册<br/>图片内角标 01、02……]
    K --> L[发送引导<br/>按编号顺序勾选 + 勾选「发送后合并展示」]
    L --> M[微信聊天出现折叠卡片]
    M --> N[收图人体验<br/>左右滑动 / 展开收起 / 微信侧保存或转发]
```

读图要点：
- F→G 之后是发送方能控制的全部（每张卡内容 + 可见编号 + 保存调用顺序）；系统相册排列和微信侧行为不可控，只能引导用户核对角标。
- 回流能力尚未实现，不能把末卡或裂变埋点写成当前事实。

### 3.1 玩法模板注册表

每个玩法是一个注册项：

```js
{
  id: 'fun-text-stack',        // 玩法唯一 ID（埋点维度）
  name: '趣味字画',
  inputType: 'text',           // text | images | template-params | mixed
  composeFn: 'composeScenes',  // 结构化场景的卡片生成函数
  cardCountRule: '按叙事策略生成 3–8 张卡',
  minCards: 3,                 // ≥3 张硬约束
  fallbackStrategy: '规则故事模板',
  trackDimension: { moduleId: 'fun-text-stack', strategyId: null }
}
```

新玩法 = 在注册表新增一个注册项，接入管线既有组件。

### 3.2 通用组件清单（底座能力）

| 组件 | 说明 | 现状 |
| --- | --- | --- |
| 编号保存 | 把 01、02……写入最终图片，并按 manifest 顺序保存到相册 | 已实现：`stackExportManifest.js` + `sequenceBadgeComposer.js` + `imageExporter.saveExportManifest`，覆盖穿搭叠图和趣味字画；待真机验收 |
| 发送引导浮层 | 教用户“每次只发送一叠 + 按图片角标勾选 + 确认 01 在第一位 + 勾选「发送后合并展示」” | 三个结果页已统一文案；待真实微信聊天验收 |
| 回流卡生成器 | 生成末卡“用 WePicTool 做同款”，可开关 | 规划，未实现 |
| msgSecCheck 接入点 | 用户输入文字的内容安全检测 | 分支已实现；生产权限和异常仍待验收 |

### 3.3 埋点体系

当前分支尚无统一事件上报模块。以下是规划事件，不代表已经采集；实施前需另写设计和隐私口径。

| 事件 | 说明 |
| --- | --- |
| `module_entered` | 进入某功能模块（带模块 ID） |
| `template_used` | 使用某玩法模板（带模板 ID） |
| `stack_saved` | 一叠图保存完成（带张数、玩法类型） |
| `send_guide_completed` | 看完发送引导并去发送 |
| `reflow_card_impression` | 回流引导卡随叠图生成/预览曝光 |
| `reflow_card_toggled` | 用户打开/关闭回流引导卡开关 |

**按玩法维度看漏斗：** `module_entered` → `template_used` → `stack_saved` → `send_guide_completed` → 分享转化，决定模板库加码方向。回流卡单独统计曝光与开关，验证"收到图的人转化为新用户"的裂变链路。

### 3.4 叠图预览组件

预览组件是所有玩法共用的朋友视角预演，不是微信聊天本身。当前确认口径为：

- 只使用真实系统状态栏和小程序胶囊，不再绘制第二套时间或右上菜单；
- 会话导航和底部“预览模式”栏固定，中间聊天消息区是唯一纵向滚动区；
- 每叠作为一条右侧图片消息，头像固定；“展开 N”紧贴对应牌堆；
- 图片按消息通道和原始比例等比展示，不再使用 `54vw / 150px / 164px` 固定小舞台；
- 横向手势只移动当前叠顶层图，纵向手势交还聊天区；预览翻页不修改项目顺序；
- 展开从当前顶层开始，收起保持当前顶层；单张可看大图；
- 长按只提供可兑现的“保存这张/保存这一组”，不伪装图片组直接转发；
- 普通/深色模式使用独立仿真主题；图片内 `01…N` 始终是顺序事实源。

完整产品设计见 `../superpowers/specs/2026-09-05-wechat-preview-simulation-redesign.md`，当前实现契约见 `TECHNICAL_SPEC.md` §12.6。真机与真实微信差异必须记录，不能把“高仿真”写成像素级保证。

## 4. 模块实现卡

首页固定为：**任务选择 → 单一共享预览 → 当前玩法双行动 → 更多工具**。模块卡描述玩法，不再决定首页层级。

| 模块 | 一句话说明 | 是否依赖 AI | 建议阶段 |
| --- | --- | --- | --- |
| 穿搭叠图 | 头像/上衣/下装/鞋子各成一叠；手动分层或 AI 整理后混合编辑 | 否，AI 是可选增强 | 当前分支已实现，待外部验收 |
| 趣味字画 | 输入一句话，自动生成三套有节奏、可编辑的字画滑卡 | 可选（规则兜底） | P2.1 分支代码/自动化完成；P2.2 为计划外实验 |
| 剧情反转 | 使用更长的故事模板，滑到最后有反转 | 可复用趣味字画规划器 | 后续 P4 |
| 盲盒抽卡 | 聚会抽签、答案之书，滑停在哪张算哪张 | 否 | 阶段七 |
| 拼图揭秘 | 大图切块，封面悬念，展开拼全图 | 否 | 阶段七 |
| 资料打包 | 多张照片分组多叠 + 封面目录卡，防刷屏 | 否 | 阶段七 |
| 翻页动画 | GIF/视频抽帧，滑一滑就"播放" | 弱（抽帧为主） | 阶段八 |
| 成套搭配 / 滑滑换装 / 独立 AI 穿搭入口 | 已合并为当前「穿搭叠图」工作台，不再作为多个独立入口 | 不适用 | 已替代 |

每张卡按固定 6 段结构编写：① 对标效果 ② 输入 → 输出 ③ 收图人体验 ④ 技术实现路径 ⑤ 依赖与风险 ⑥ 验收标准。

### 4.1 穿搭叠图（旗舰）

**① 对标效果：** 微信官方文章"研究穿搭"演示——白底分组卡片叠图，朋友左右滑动对比上衣/下装/鞋。官方示例已验证白底分组卡片是叠图最有质感的用法，但用户自己拍的照片背景杂乱，直接发不出手。

**② 输入 → 输出：** 用户进入同一个四部位工作台，可直接选择部位添加图片，也可一次选 1–9 张混合图片交给 AI 分类、去背和统一白底；AI 结果先进入复核页，可改单张分类、删除、切换原图/白底，再追加回工作台。低置信度、其他类别或部位已满的图片进入待确认区，由用户指定部位。两种添加方式可反复混用，最终仍按头像/发型、上衣、下装、鞋子四组排序、预览和编号保存。比例默认 4:5，只影响 AI 白底卡片。

**③ 收图人体验：** 先收到上衣组叠图（白底卡逐张滑），再下装组、鞋子组；每组封面即第一件单品，滑动节奏 = 逐件对比，可回复"上衣 1 + 下装 2"。

**④ 技术实现路径：** 已实现、待真机验收。手动图片直接进入 `layeredDressup` 项目；AI 子流程为 `outfit-import` → `wx.chooseMedia` → 前端压缩 → 云存储 → `processOutfit` 分类/抠图 → 人工复核 → eventChannel 追加到同一项目。之后统一走 manifest、可见序号物化、微信预览、串行保存和发送引导。`ENABLE_OUTFIT_AI_ASSIST=false` 时只隐藏 AI 添加方式，不影响手动主链路。

**⑤ 依赖与风险：** 抠图边缘质量（生成模型非专业分割，保留原图兜底）；浅色衣物白底可见性（轻阴影 + 细描边已实现，真机验证）；前端 Canvas 大图内存（iOS/Android 待验证）。

**⑥ 验收标准：** 状态为**已实现待真机验收**；每次验证结果记录在当天 `docs/iterations/` 日志中，并按以下口径逐项过：

- 用 20 张穿搭素材测试，白底结果可接受率 >= 70%。
- 白色 / 浅色衣物在白底上仍然可辨认。
- 单张处理端到端 <= 10 秒；3 张 <= 20 秒。
- 失败图不影响其他结果展示。
- 按组保存真机通过；1:1 / 4:5 / 3:4 三种比例切换真机可用。
- iOS + Android 真机各跑一遍。
- 叠加定位口径：真机勾选「发送后合并展示」后与官方"研究穿搭"演示逐项对比（封面、滑动、展开/收起、一键保存全部）。

### 4.2 趣味字画（替代大字滑卡）

**① 对标效果：** 保留微信逐字卡和“滑到最后揭晓”的直观乐趣，但不再机械地一字一图。产品围绕封面悬念、滑动停顿、反转落点和手账式视觉，把一句普通聊天文字改编成一叠有节奏的表达。

**② 输入 → 输出：** 用户可从 6 类 12 个结构化案例取灵感，也可以直接输入一句话并选择“搞怪反转 / 可爱直球 / 嘴硬心软”等表达标签 → 系统从 8 种规则叙事玩法中选出三种不同结构 → 规则模板（以及待确认发布范围的 AI 实验）输出三套 3–8 张故事计划 → 自动匹配 7 套视觉包并生成真实可滑候选 → 用户选一套直接保存，或进入「内容 / 样式 / 装饰」聚焦编辑。编辑支持单卡/整组背景、成套配色与 3 种字感，装饰拖动/双指缩放/旋转，以及 20 步撤销重做；不提供任意 RGB、自由画笔或无限图层。封面由 `hook` 卡承担，末段由 `reveal` 或 `ending` 卡形成落点。

**③ 收图人体验：** 第一张让人愿意继续滑，中间通过短句、留白或涂鸦形成停顿，最后一至两张揭晓原意或制造可爱反转。三套候选不是换色，而是嘴硬反转、悬念揭晓、伪清单等不同表达方式。

**④ 技术实现路径：** P2.1/P2.3 分支代码采用规则规划 + 确定性场景渲染；案例、策略、视觉包、配色、字体和装饰全部来自白名单注册表。`candidateValidator` 检查卡数、角色、长度、原意和安全，`sceneComposer` 把角色与视觉包转换为背景及文字/贴纸/涂鸦图层；项目模型用不可变变更和非递归快照维护最近 20 步历史，手势仅在结束时提交一次。小程序按场景 `fontKey` 加载字体，`fun-card-renderer` 用同一键输出 1080×1080 PNG，任一端字体不可用时都不得静默换成系统字体。P2.2 分支实验让 AI 只生成故事计划、不生成最终中文图片，并在异常时回落规则模板；它不在已确认的阶段一计划内，`planFunTextStory` 尚未部署，服务端模型 API key 和发布范围也未确认。

**⑤ 依赖与风险：** 难点不是字体数量，而是三套候选的真实差异、原意保留、预览与高清图一致、素材权利和轻编辑边界。旧 `codex/bigtext-handwrite` 只选择性迁移授权字体、渲染、贴纸和失败清理，不整体合入旧页面和逐字任务模型。Docker/Linux 原生依赖、CloudBase 权限与私密入口、HTTPS 字体域名、48 小时清理规则和真机内存/渲染表现都尚未验证。

**⑥ 验收标准：** 当前只有代码和自动化证据，尚未发布。最终仍需：首页示例无需输入即可理解；输入一句话后最多再做一次选择就看到三套可滑候选；三套策略和视觉明显不同；关闭 AI 仍能完成；编辑不暴露通用画布参数；微信开发者工具、iOS/Android 完成预览、高清渲染、按序保存和真实微信发送。未实际执行的项必须记录为“未验证”。

完整产品、交互、数据和技术设计见 `../superpowers/specs/2026-08-31-fun-text-stack-design.md`。

### 4.3 剧情反转

**① 对标效果：** 微信官方"整蛊朋友"演示（13 张"右滑 → 再滑 → 出去。"）——逐张节奏引导 + 末尾反转。

**② 输入 → 输出：** 用户选模板（整蛊 / 表白 / 生日倒数 / 道歉反转）→ 填入称呼或名字、可上传最后一张图 → 复用趣味字画的叙事策略、卡片角色和场景系统生成 6–13 张节奏卡 → 编号保存。封面 = `hook` 卡，顺序 = 故事计划定义的节奏序列。

**③ 收图人体验：** 封面勾起好奇 → 每张一句短句，停顿节奏由模板控制 → 末张反转。反转结构自带转发——收到的人一定会问"这怎么做的"，是最强的裂变引擎。

**④ 技术实现路径：** 不再单独建设第二套模板引擎。剧情模板作为趣味字画策略注册项，声明固定槽位、卡片角色、停顿和末图位置；`creativePlanner` 可填充结构化文案，规则模板永久兜底；`sceneComposer` 和云端高清渲染完全复用。用户填写和模型新增文字均经过内容安全门禁，埋点按策略/模板 ID 统计。

**⑤ 依赖与风险：** 整蛊只做可爱反转，不做恐怖惊吓（红线 2）；用户自定义称呼过安全检测；模板文案需审核把关，避免擦边内容。

**⑥ 验收标准：** 真机用每个模板生成 → 发送 → 与官方"整蛊朋友"13 张演示对比节奏结构（封面悬念 → 逐张引导 → 末张反转）一致；自定义称呼出现在正确卡位；末图（如上传）位置正确；埋点 `template_used` 带模板 ID 上报。

### 4.4 盲盒抽卡

**① 对标效果：** 叠图"滑停"动作即抽签——一叠卡背统一的卡，每个人滑停在哪张算哪张（官方"合并发图"玩法的互动变体）。

**② 输入 → 输出：** 用户选玩法（聚会抽签 / 答案之书 / 今日运势）→ 设置选项数量和内容（或用预设）→ 生成卡背统一的一叠 → 发到群里。**选项不足 3 个时自动补空卡/引导卡凑满 3 张**（兜底策略）。封面 = 统一卡背，顺序 = 前端打乱后的顺序。

**③ 收图人体验：** 看到一叠卡背，凭感觉滑停在某张，翻开即是自己的"签"；互动即拉新。

**④ 技术实现路径：** 纯前端。统一卡背模板 + 选项卡渲染，顺序在前端打乱；不需要 AI 和云函数；自定义选项文字过 `msgSecCheck`。

**⑤ 依赖与风险：** 自定义选项必须过安全检测；"答案之书"类文案避免迷信敏感表述，走轻松娱乐口径。

**⑥ 验收标准：** 真机生成一叠 → 卡背全部一致 → 滑停在任意张可查看对应选项；选项不足 3 个时自动补满 3 张；打乱顺序后保存编号与滑停结果一致；不当选项文字被拦截。

### 4.5 拼图揭秘

**① 对标效果：** 利用叠图"双形态"——封面只露一块碎片制造悬念，展开后拼出完整大图（对官方折叠卡片展开/收起形态的玩法化使用）。

**② 输入 → 输出：** 用户上传一张大图 → 选切分数量（3 / 6 / 9 块）→ 生成切块卡序列，编号保存。封面 = 第 1 块（一角），顺序 = 展开后的阅读顺序。

**③ 收图人体验：** 封面只看到一角（悬念）→ 滑动逐块浮现 → 展开态拼出全图（惊喜落点）。适合海报预告、宝宝照片、惊喜礼物揭秘。

**④ 技术实现路径：** 纯前端 Canvas 裁切；**关键是切块顺序与编号映射要对应展开后的阅读顺序**（先行后列）；发送引导复用管线。

**⑤ 依赖与风险：** 微信折叠卡片展开态的排版间隙会断开拼图，需要在验收时确认真机展开观感；大图裁切后的单块尺寸不能小到看不清。

**⑥ 验收标准：** 真机 3/6/9 块各生成一叠 → 封面只露一角 → 展开态按阅读顺序能拼回完整大图；编号顺序与展开顺序映射正确；与官方折叠卡片双形态逐项对比。

### 4.6 资料打包

**① 对标效果：** 微信官方自己的卖点"避免照片轰炸"——多叠合并发送 + 每叠封面目录卡，对方一键保存全部。

**② 输入 → 输出：** 用户选 9–50 张照片 → 分组（v1 只做**手动分组**）→ 每组自动生成封面目录卡（标题 + 日期 + 张数）→ 多叠编号保存 → 依次合并发送。

**③ 收图人体验：** 不再被几十张图刷屏；每叠封面目录卡一眼看清"这组是什么、几张"；可一键保存全部。

**④ 技术实现路径：** 分组逻辑 + Canvas 封面目录卡生成；`wx.chooseMedia` 单次上限 9 张，需分批选择；无 AI；可与「记录」页打通复用历史分组。

**⑤ 依赖与风险：**

- **"按时间分组"降级：** `wx.chooseMedia` 拿不到可靠拍摄时间（无 EXIF 回传），**v1 只做手动分组，时间分组标记"待验证"**，不进入首版承诺。
- **分批选择：** 超过 9 张需分多次调用 `wx.chooseMedia`，需做已选列表管理。
- 张数上限受相册保存与发送操作负担约束，v1 上限 50 张。

**⑥ 验收标准：** 真机分批选 20+ 张 → 手动分 3 组 → 每组封面目录卡信息正确（标题 + 张数）→ 多叠保存编号清晰 → 依次合并发送后对方可一键保存全部；不出现"按时间分组"入口（待验证标记仅在文档中）。

### 4.7 翻页动画

**① 对标效果：** 微信官方"隔空一拳"演示（3 帧出拳）——快速滑动时帧序列形成"播放"效果，是官方玩法里视觉冲击力最强、但普通人完全做不了的（抽帧、排序、节奏都太麻烦）。门槛越高，工具价值越大。

**② 输入 → 输出：** 用户上传 GIF 或 3 秒内短视频（或直接选动作素材库：出拳 / 比心 / 变装）→ 抽帧成 8–24 张 → 预览滑动播放效果 → 编号保存。封面 = 第 1 帧，顺序 = 时间正序。

**③ 收图人体验：** 快速滑动时画面"动起来"——一拳挥出、一颗心比出来。**帧数甜点区间 8–12 帧**；上限 24 帧，手动滑 24 帧体验差（手酸、节奏拖沓），不得超出。

**④ 技术实现路径：** 两条路线——

1. **素材库先行（v1）：** 预置若干动作帧序列（出拳 / 比心 / 变装），用户零等待直接用，纯前端。
2. **自定义抽帧（v2）：** 小程序端视频抽帧兼容性差，走**云托管跑 ffmpeg** 抽帧后回传帧序列。云托管是容器制，可跑 ffmpeg，绕开 CloudBase 云函数不支持原生模块的限制（sharp 错误码 145 同因）。

先上①验证玩法，再加②；**路线②上线前需做一次云托管抽帧验证（耗时 / 回传体积 / 费用）**。

**⑤ 依赖与风险：** 路线②是 spike 项：云托管冷启动耗时、帧序列回传体积（8–12 张图的流量成本）、云托管计费模式均需实测；用户上传视频内容需注意审核口径。

**⑥ 验收标准：** 素材库路线：真机选素材 → 生成 8–12 帧 → 快速滑动有明确"播放"感 → 与官方"隔空一拳"对比动效成立。自定义抽帧路线：云托管抽帧验证报告（耗时 / 体积 / 费用）产出后，真机上传 3 秒视频 → 抽帧张数在甜点区间 → 滑动播放流畅。

### 4.8 成套搭配

**① 对标效果：** 穿搭主线自然深化——从"分组发单品"升级为"发成套搭配"，朋友直接回复"第 2 套"（官方"研究穿搭"演示的进阶用法）。

**② 输入 → 输出：** 基于本次上传或历史衣物 → 自动/手动组合 N 套 → 一套一叠（上衣 1 + 下装 1 + 鞋 1）→ 多叠编号保存发送。每叠封面 = 该套第 1 件，顺序 = 上衣 → 下装 → 鞋。

**③ 收图人体验：** 一叠 = 一套完整搭配，滑 3 张看完一套；多叠对比后直接回复"第 2 套"，与阶段四编号角标、投票场景打通。

**④ 技术实现路径：** 复用穿搭管线全部能力（分类 + 抠图 + 白底卡 + 编号保存），增量只有**组合逻辑**（N 件上衣 × M 件下装排列 + 手动调整）和**多叠保存**。**建议等穿搭主链路留存数据稳定后再做。**

**⑤ 依赖与风险：** 单套只有 3 张（上衣 + 下装 + 鞋），恰好满足 ≥3 张硬约束，但某组缺图时（如无鞋）需自动补封面卡凑满；组合数爆炸需限制 N 套上限。

**⑥ 验收标准：** 真机上传 3 上衣 × 2 下装 → 生成多套 → 每叠 ≥3 张（缺组自动补卡）→ 多叠发送后朋友可按叠回复编号；与官方"研究穿搭"演示对比单叠观感一致。

### 4.9 滑滑换装

**① 对标效果：** 滑动交互和换装是天生一对——封面人台固定，每滑一张换一套，像芭比换装（叠图帧序列玩法与穿搭主线汇合的"大杀器"）。

**② 输入 → 输出：** 用户选一个虚拟人台（或上传自己的照片）→ 从衣柜挑几套 → 生成"人台不变、衣服在变"的帧序列 → 发送后朋友滑一滑帮你选。封面 = 人台 + 第 1 套，顺序 = 套数顺序，套数不足 3 时补封面/引导卡凑满 3 张。

**③ 收图人体验：** 人台位置固定不动，滑一下换一套衣服，对比极其直观；最后可以停在最喜欢的一套截图回复。

**④ 技术实现路径：** 依赖抠图质量——衣物白底图叠加到人台对应位置：**上衣锚点偏上、下装锚点偏下，复用现有分组锚点体系**（`cardComposer.js` 的 `GROUP_ANCHOR`）；进阶可接 AI 试穿 API 生成真实上身效果。**放最后做，等阶段三抠图质量验证通过后启动。**

**⑤ 依赖与风险：** 抠图边缘质量直接决定换装观感（spike：阶段三真机验收的抠图质量结论）；上传真人照片有隐私与审核风险，v1 建议只做虚拟人台；AI 试穿 API 的成本与合规待评估。

**⑥ 验收标准：** 真机选人台 + 3 套衣服 → 帧序列人台位置不变、衣服逐套切换 → 滑动换装节奏成立；套数不足 3 时自动补卡；与官方叠图滑动体验对比无明显违和。

## 5. 上线节奏

```text
P0：共享底座真机验收与上线范围
  → 先稳定所有玩法都依赖的预览、保存、安全和发送引导
P1：穿搭叠图 + 玩法/素材注册底座
  → 完成已确认的旗舰玩法升级和内置试玩
P2：趣味字画
  → 规则闭环 → AI 结构化规划 → 轻量编辑，替代旧大字滑卡
P3：胶片相册 → 前后对比 → 无缝画卷
  → 优先实现复用率高、无 AI 强依赖的照片玩法
P4：翻页动画 + 剧情反转 + 盲盒抽签
  → 复用趣味字画的策略、场景和素材系统
P5：资料打包、拼图揭秘、自由手绘等兴趣实验
```

**排期逻辑：** 先把共享底座和已确认的分层换装收口，再以趣味字画建立“策略计划 → 场景渲染 → 轻量编辑”的第二条可复用主线。剧情反转不再单独建设一套模板引擎，后续直接复用趣味字画的策略和场景系统。当前进入条件和完成口径以 `docs/roadmap.md` 为准。
